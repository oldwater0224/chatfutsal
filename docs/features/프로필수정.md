# 프로필 수정 기능명세서

> GitHub Issue: #58

## 1. 개요

가입 후 닉네임(`displayName`)을 바꿀 수 있게 한다. 지금은 가입 시 입력한 이름을 바꿀 방법이 없다.

### 범위

| 항목 | 상태 |
|---|---|
| 닉네임 변경 (`/mypage/profile`) | **이번 작업** |
| `userService.ts` 신설 (`users` 문서 쓰기 경로) | **이번 작업** |
| 실력 수준(레벨) 표시 | **보류** — 저장 위치·설계를 더 검토한 뒤 결정 (7장) |
| 포지션 | **제외** — 필요하지 않음 |
| 프로필 이미지 업로드 | **제외** — Firebase Storage 설정이 필요해 별도 과제 |

`User` 타입은 바꾸지 않는다.

## 2. 화면

### 2-1. 진입

`/mypage` → **계정** 섹션 → "프로필 수정" → `/mypage/profile`

### 2-2. `/mypage/profile`

```
┌ SubHeader: 프로필 수정 ┐
│ 닉네임                  │
│ [ 현재 닉네임        ]  │
│ 2~12자                  │
│ (오류 메시지)           │
├─────────────────────────┤
│ [        저장        ]  │  ← 바뀐 게 없거나 형식이 틀리면 비활성
└─────────────────────────┘
```

- 비로그인 → `/login`으로 이동 (`/mypage`와 같은 방식)
- 저장 성공 → `/mypage`로 이동. `/mypage`가 다시 마운트되며 `users` 문서를 새로 읽으므로 바뀐 이름이 바로 보인다
- 저장 실패 → 입력값은 유지하고 오류 메시지를 표시

## 3. 닉네임 규칙

`src/lib/services/userRules.ts`의 순수 함수 `validateDisplayName(raw, current)`로 판정한다. 화면과 서비스가 같은 함수를 쓴다.

| 조건 | 결과 |
|---|---|
| 앞뒤 공백 제거 후 저장 | `"  풋살러 "` → `"풋살러"` |
| 2자 미만 / 12자 초과 | 오류: "닉네임은 2~12자로 입력해주세요." |
| 금지 문자 포함 | 오류: "닉네임에 쓸 수 없는 문자가 들어 있어요." |
| 현재 닉네임과 같음 | 오류는 아니지만 저장할 것이 없음 (`unchanged`) → 저장 버튼 비활성 |

글자 수는 `Array.from()`으로 센다 (이모지 등 서로게이트 쌍을 한 글자로 계산).

**금지 문자**: C0 제어문자(U+0000-001F)·DEL(U+007F), 보이지 않는 문자(U+200B, U+2060, U+FEFF),
방향 제어 문자(U+202A-202E, U+2066-2069). 이름을 뒤집어 보이게 하거나 빈 이름처럼 보이게 하는 데 쓰인다.
ZWJ(U+200D)는 이모지 조합(👨‍👩)에 쓰이므로 허용한다. "관리자" 같은 예약어는 막지 않는다.

같은 파일의 다른 함수:

| 함수 | 쓰는 곳 |
|---|---|
| `isValidDisplayName(value)` | 저장된 값이 현재 규칙에 맞는지 (푸시 제목, `푸시알림.md` 4-2) |
| `toInitialDisplayName(raw, fallback = "카카오 사용자")` | 카카오 로그인 API가 카카오 닉네임을 최초 닉네임으로 다듬는다. 금지 문자 제거 → 앞뒤 공백 제거 → 12자로 자름 → 그래도 맞지 않으면 기본값 |
| `nameForCopy(displayName)` | 다른 문서에 복사할 이름. `users` 문서 닉네임 그대로, 없으면 `"사용자"` (5장) |

가입 화면(`/signup`)도 계정을 만들기 전에 `validateDisplayName`으로 검사하고 공백을 제거한 값을 저장한다.

## 4. 저장 흐름

```
/mypage/profile 저장
  → validateDisplayName() 통과
  → userService.updateDisplayName(authUser, name)
      1. updateDoc(users/{uid}, { displayName })   ← Firestore
      2. updateProfile(authUser, { displayName })  ← Firebase Auth
```

**두 곳을 모두 바꾸는 이유:** 앱이 닉네임을 두 출처에서 읽는다.

| 출처 | 쓰는 곳 |
|---|---|
| Firestore `users/{uid}.displayName` (`useAuth().userData`) | 마이페이지, 모집글 작성(`authorName`), 참가 신청(`applicantName`), 채팅방 이름(`participantNames`), 다른 사용자 프로필, 사용자 검색 |
| Firebase Auth `user.displayName` (`useAuth().user`) | 헤더 아바타, 채팅 메시지(`senderName`), 프로필에서 채팅 시작 |

Firestore를 먼저 쓴다. 다른 사용자에게 보이는 원본이기 때문이다. Auth 갱신이 실패하면 오류를 표시하고, 다시 저장하면 두 곳이 모두 맞춰진다.

부수 효과: 카카오 로그인 사용자는 커스텀 토큰으로 로그인해서 Auth `displayName`이 비어 있다 (헤더 "U", 채팅 "사용자"로 표시). 닉네임을 한 번 저장하면 Auth에도 이름이 들어가 이 표시가 바로잡힌다.

## 5. 이미 저장된 이름 (비정규화)

`displayName`은 다음 문서에 복사되어 있다. **채팅방만 갱신하고 나머지는 그대로 둔다** (이슈 #58의 1안 + 채팅방 예외).

| 위치 | 필드 | 변경 후 |
|---|---|---|
| `chatRooms` | `participantNames[uid]` | **갱신** (5-1) |
| `recruitPosts` | `authorName` | 기존 글은 옛 이름, 새 글부터 새 이름 |
| `applications` | `applicantName` | 기존 신청은 옛 이름, 새 신청부터 새 이름 |
| `messages` | `senderName` | 기존 메시지는 옛 이름, 새 메시지부터 새 이름 (채팅 화면에는 표시되지 않음) |

**새로 복사할 때는 항상 `users` 문서 값을 쓴다.** 보안 규칙(6장)이 `authorName`·`applicantName`·`participantNames` 값을
작성자(각 참여자)의 `users/{uid}.displayName` 또는 `"사용자"`로만 허용하므로, 서비스가 쓰기 직전에 `users` 문서를 읽어
`nameForCopy`로 정한다. 화면이 넘기는 이름 인자(`createRecruitPost`의 `authorName`, `applyToPost`의 `applicantName`,
`startChat`/`createChatRoom`의 `displayName`)는 호출부 호환을 위해 남겨 두었지만 쓰지 않는다.
화면의 `userData`는 마운트할 때 한 번 읽은 값이라 다른 탭에서 닉네임을 바꾸면 오래된 값일 수 있고,
Auth 프로필 이름은 `users` 문서와 다를 수 있기 때문이다.

| 서비스 | 읽는 방법 |
|---|---|
| `recruitService.createRecruitPost` | `getDoc(users/{authorId})` |
| `applicationService.applyToPost` | 트랜잭션 안에서 `tx.get(users/{applicantId})` (알림 제목의 이름도 같은 값) |
| `chatService.createChatRoom` | 두 참여자의 `users` 문서를 함께 읽는다 |
| `chatService.startChat` (기존 방) | 내 `users` 문서 닉네임이 있을 때만 내 항목을 바로잡는다 |

일괄 갱신(2안)을 전부 택하지 않은 이유: 보안 규칙상 `applications`는 다른 사용자 문서라 클라이언트에서 고칠 수 없다. 표시 시점 조회(3안)는 목록마다 `users` 읽기가 늘고 페이지네이션과 맞지 않는다.

한계: 모집글·신청 목록에는 옛 이름과 새 이름이 섞여 보일 수 있다. 필요해지면 서버 작업으로 일괄 갱신하는 방안을 검토한다.

### 5-1. 채팅방 이름

채팅 목록과 채팅방 상단은 `participantNames[상대 uid]`로 상대 이름을 보여준다. 1:1 대화에서 옛 이름이 보이면 다른 사람으로 오해할 수 있어 갱신한다.

| 시점 | 동작 |
|---|---|
| 닉네임 저장 | `chatService.updateMyNameInChatRooms` — 내가 참여한 방(`participants array-contains uid`)마다 내 항목을 갱신. **방마다 따로 써서**(`Promise.allSettled`) 한 방이 실패해도 나머지는 반영된다. 실패는 로그만 남기고 닉네임 변경은 성공으로 처리 |
| 기존 방에서 채팅 다시 시작 | `startChat`이 저장된 내 이름이 현재 닉네임과 다르면 바로잡는다 (위에서 빠진 방 보정). 실패해도 채팅은 연다 |
| 새 방 생성 | 두 참여자 모두 `users` 문서의 현재 닉네임 (없으면 `"사용자"`). `createChatRoom`이 직접 읽는다 |
| 채팅방 화면 | `getDoc` 대신 `onSnapshot`으로 구독해 대화 중 상대가 이름을 바꿔도 바로 반영 |

채팅 목록은 원래 `onSnapshot`으로 구독 중이라 별도 작업이 없다.

## 6. 보안 규칙

### 6-1. `users` 닉네임 형식 (`validName`)

클라이언트 규칙(3장)과 같은 내용을 규칙에서도 검사한다.

```
function validName(v) {
  return v is string
    && v.size() >= 2
    && v.size() <= 24
    && v.trim() == v
    && !v.matches('(?s).*[\\x{0}-\\x{1F}\\x{7F}\\x{200B}\\x{2060}\\x{FEFF}\\x{202A}-\\x{202E}\\x{2066}-\\x{2069}].*');
}
```

- 규칙의 `size()`는 UTF-16 코드 단위를 센다. 클라이언트의 12자(코드 포인트)는 최대 24단위이므로 상한을 24로 둔다 (이모지 12개 = 24단위 허용, 13개 거부). 그래서 규칙은 클라이언트보다 조금 느슨하다 (예: 한글 13~24자는 규칙만 통과)
- `create`: `validName(displayName)` 필수
- `update`: `displayName`이 `affectedKeys`에 있을 때만 검사한다 (`nameUnchangedOrValid`). 예전 규칙으로 저장된 긴 닉네임이 있어도 다른 필드는 바꿀 수 있다. 닉네임 삭제는 `validName(null)`이 거짓이라 막힌다

### 6-2. 복사된 이름 (`copiedNameOf`)

```
function copiedNameOf(v, uid) {
  return v is string
    && (v == '사용자'
      || (exists(/databases/$(database)/documents/users/$(uid))
        && get(/databases/$(database)/documents/users/$(uid)).data.get('displayName', null) == v));
}
```

| 위치 | 조건 |
|---|---|
| `recruitPosts` create | `authorName`이 작성자의 `copiedNameOf` (없으면 거부) |
| `recruitPosts` update (작성자) | `authorName`이 바뀔 때만 검사. 글을 쓴 뒤 닉네임을 바꿔도 다른 필드는 수정할 수 있다. 삭제는 거부 |
| `applications` create | `applicantName`이 신청자의 `copiedNameOf` |
| `chatRooms` create | `participantNames` 키는 `participants`의 부분집합, 각 값은 그 참여자의 `copiedNameOf` (항목이 없으면 화면이 `"사용자"`로 보여 주므로 허용) |

형식 검사는 하지 않는다. 예전에 저장된 긴 닉네임도 `users` 문서와 같으면 복사할 수 있다.
`"사용자"`는 누구나 쓸 수 있는 기본값이다. `get()` 읽기가 1~2회 늘어난다.
`messages.senderName`은 검사하지 않는다 (채팅 화면에 표시되지 않음).

### 6-3. 채팅방 내 이름 갱신

`chatRooms` update에서 참여자는 `participantNames`에서 **내 항목만**, **내 `users` 문서의 현재 닉네임과 같은 값으로만** 바꿀 수 있다 (`get()` 읽기 1회 추가). 다른 필드와 함께 바꿀 수 없다. 이 경로에는 형식 검사를 넣지 않았다.

```
function changesOnlyOwnName() {
  return changedOnly(['participantNames'])
    && request.resource.data.participantNames.diff(resource.data.participantNames)
         .affectedKeys().hasOnly([request.auth.uid])
    && request.resource.data.participantNames[request.auth.uid]
         == get(/databases/$(database)/documents/users/$(request.auth.uid)).data.displayName;
}
```

`users` 문서는 로그인 사용자 전체가 읽을 수 있으므로 민감한 필드를 추가하지 않는다.

## 7. 보류: 실력 수준(레벨)

모집글에는 이미 `beginner / amateur / semipro / pro` 레벨(`LEVEL_LABELS`, `LEVEL_COLORS`)이 있다.
사용자 프로필에 레벨을 표시하려면 값을 어디에 둘지(사용자가 직접 고르는 값 / 활동에서 파생 등)부터 정해야 해서 이번 작업에서 뺐다. 설계가 정해지면 이 문서에 이어서 기록한다.
