## 상세

### 1. "조건에 맞는 글 더 찾기" 버튼이 눌러도 동작하지 않을 수 있음
`src/hooks/useRecruitPosts.ts` (`requestMore`, 자동 이어 받기 effect)

- 자동으로 다음 페이지를 이어 받았는데 새로 맞는 글이 0개면, 버튼을 눌러도 목표 개수(현재 글 수 + 20)가 이전과 같은 값으로 계산된다
- 이어 받을 페이지 수 한도는 목표 개수가 바뀔 때만 다시 채워지므로, 버튼은 보이는데 아무 일도 일어나지 않는다
- 예: 검색어가 앞쪽 5페이지 안에서 하나도 맞지 않으면 버튼을 계속 눌러도 반응이 없다
- 판단: 실제 버그. 버튼을 누를 때마다 한도를 다시 채우도록 고친다

### 2. 실시간 구간의 끝과 이어 받기 시작점이 어긋나 글이 하나 빠질 수 있음
`src/hooks/useLivePagedQuery.ts` (`loadMore`)

- 이어 받기 시작점(커서)은 렌더할 때의 마지막 문서로, 실시간 구간의 끝(앵커)은 `setState` 안에서 최신 상태의 마지막 문서로 정한다
- 그 사이 새 글이 들어와 마지막 문서가 바뀌면 둘이 달라진다. 예를 들어 20번째 글이 실시간 구간에서 밀려나면 실시간 쪽(`endAt(19번째)`)에도 이어 받은 쪽(`startAfter(20번째)`)에도 들어가지 않아 화면에서 사라진다
- 판단: 실제 버그. 시작점과 끝을 같은 문서로 정한다

### 3. 더 보기가 거의 동시에 두 번 실행되면 같은 페이지가 중복으로 붙음
`src/hooks/useLivePagedQuery.ts` (`loadMore`), `src/hooks/pagedQuery.ts` (`mergePages`)

- 중복 실행 방지가 렌더 시점의 `loadingMore` 값을 보고 있어서, 화면이 갱신되기 전에 두 번 불리면 둘 다 통과한다
- `mergePages`는 실시간 구간과 이어 받은 구간 사이의 중복만 제거하고, 이어 받은 구간 안의 중복은 제거하지 않는다. 같은 글 20개가 두 번 보이고 React에서 key 중복 경고가 난다
- 더블클릭, StrictMode, 자동 이어 받기 effect 재실행에서 생길 수 있다
- 판단: 실제 버그. `ref`로 중복 실행을 막고, 이어 받은 구간 안에서도 중복을 제거한다

### 4. 이어 받기 실패 시 연달아 재시도하고, 이미 보이던 목록이 가려질 수 있음
`src/hooks/useRecruitPosts.ts`

- 요청이 실패해도 "더 있음" 상태가 그대로라 자동 이어 받기가 한도 5번을 연속 실패로 다 쓴다
- 실패 원인이 `permission-denied`면, 이미 불러온 글이 있어도 로그인 안내 화면으로 바뀐다
- 판단: 이어 받기 오류를 첫 페이지 오류와 분리하고, 실패하면 자동 재시도를 멈춘다

### 5. 실시간 구독이 실패해도 이전 목록이 그대로 남음
`src/hooks/useLivePagedQuery.ts`

- 이전 코드는 오류 시 목록을 비웠지만, 지금은 구독이 끊긴 뒤에도 마지막 데이터가 보인다
- 판단: 권한 오류일 때는 목록을 비우는 편이 안전하다

### 6. 더 보기를 처음 누를 때 실시간 구독을 다시 열어 첫 페이지를 다시 읽음
`src/hooks/useLivePagedQuery.ts`

- 앵커를 정하는 순간 `endAt(앵커)` 쿼리로 구독을 새로 열어 첫 페이지(메시지는 50개)를 다시 읽는다
- 새 구독의 첫 결과가 캐시에서 일부만 오면 메시지가 잠깐 사라졌다 나타나거나 스크롤이 튈 수 있다
- 판단: 비용은 한 번뿐이지만 깜빡임은 고치는 게 좋다

### 7. 날짜·실력 필터는 서버 쿼리로 걸 수 있는데 클라이언트에서 거름
`src/hooks/useRecruitPosts.ts`

- 정확히 일치하는 조건이라 `where('date','==',…)`, `where('level','==',…)`로 바꾸면 맞는 글만 읽는다
- 지금은 글이 2개뿐인 날짜를 골라도 최대 100개를 읽고, 결과가 비어 있을 수 있다
- 판단: 개선 제안. Firestore 복합 색인(`status`+`date`+`createdAt` 등) 추가가 필요하다

### 8. 이어 받은 이전 페이지는 이후 변경이 반영되지 않음
`src/hooks/useLivePagedQuery.ts`

- 이전 알림을 눌러 읽음 처리해도 화면에서는 계속 안 읽음으로 보인다. 이전 페이지의 모집글이 마감돼도 계속 보인다
- 판단: PR #62의 "남은 점"에 적어 둔 한계. 알림 읽음 표시는 화면에서 바로 반영하는 게 좋다

### 9. 같은 코드가 여러 곳에 반복됨
`src/hooks/useLivePagedQuery.ts` 외

- `initial`은 모듈 밖 함수로 충분하고, "현재 쿼리의 결과인지" 확인 코드가 4번 반복된다
- 사용하는 세 곳이 `hasMore && !loadingMore`와 오류 로그 effect를 반복한다
- 판단: 한 곳만 고치면 다른 사용자·방의 데이터가 보일 위험이 있어 정리하는 게 좋다

### 10. 자동 이어 받기가 effect 실행 횟수에 의존함
`src/hooks/useRecruitPosts.ts`

- 실시간 갱신마다 `loadMore` 함수가 새로 만들어져 effect가 다시 실행되는데, 그때 한도를 쓰는 구조라 실제 요청 없이 한도만 줄어들 수 있다
- 판단: 1번과 함께 고친다

## 이번 작업 계획 (1~3번, 10번)

1. `useLivePagedQuery.loadMore`
   - 중복 실행 방지를 `ref`로 옮긴다 (렌더 전에 두 번 불려도 한 번만 요청)
   - 커서와 앵커를 **같은 문서**로 정한다: 아직 앵커가 없으면 그 순간의 실시간 구간 마지막 문서를 앵커이자 커서로 쓰고, 이후에는 이어 받은 구간의 마지막 문서를 커서로 쓴다. `ref`로 최신 상태를 읽어 렌더 시점 값에 의존하지 않는다
2. `mergePages`: 이어 받은 구간 안의 중복도 제거한다
3. `useRecruitPosts` 자동 이어 받기
   - "더 찾기"를 누를 때마다 요청 번호를 올려 한도를 항상 다시 채운다 (목표 개수가 같아도 동작)
   - 한도 차감을 실제로 요청이 시작된 경우에만 하도록 `loadMore`가 요청 시작 여부를 돌려준다
4. 검증: 순수 함수 단위 테스트, 앵커·커서 결정 로직을 순수 함수로 분리해 테스트, `tsc`·`eslint`
