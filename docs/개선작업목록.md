## 상세

### 1. 참가 신청 트랜잭션
- `applyToPost`가 매번 새 신청 문서를 만들어, 연타·여러 탭에서 같은 유저의 신청이 중복 생성될 수 있음
- `acceptApplication`이 상태 변경 → 인원 증가 → 개수 조회 → 마감을 개별 쓰기로 처리해 동시 수락 시 정원 초과, 마감된 글에서도 수락 가능
- 중간 단계 실패 시 신청 문서와 모집글 `applicantIds`가 어긋남
- 해결: `runTransaction`으로 묶고 트랜잭션 안에서 모집글 상태·정원·중복 여부를 검증

### 2. 보안 규칙
- `firestore.rules`가 저장소에 없음
- 신청자가 남의 모집글(`applicantIds`)을 직접 수정하고, 다른 유저의 알림을 클라이언트에서 생성하는 구조라 규칙이 느슨할 가능성이 큼
- 해결: 규칙 파일을 저장소에 추가하고 역할별 수정 가능 필드를 제한 (예: 신청자는 `applicantIds`에 자기 uid만 추가·제거)
- 기존 콘솔 규칙의 `match /{document=**}` 와일드카드가 로그인 사용자에게 전체 읽기/쓰기를 허용해, 알림·유저 규칙이 사실상 무력화되어 있었음
- 검증: `npm run test:rules` (Firestore 에뮬레이터, Java 필요)
  - macOS에서 `brew install openjdk`는 keg-only로 설치되어 PATH에 잡히지 않는다.
    `PATH="/opt/homebrew/opt/openjdk/bin:$PATH" npm run test:rules`로 실행한다
- 남은 점: `applications`는 모집글 상세에서 postId로 조회하므로 로그인 사용자 전체 읽기 허용. `users` 문서의 `email`도 로그인 사용자 전체에 읽힘
- 주의: 시드 스크립트(`src/lib/seed`)는 다른 유저 명의로 글을 만들므로 새 규칙에서는 클라이언트로 실행 불가

### 3. 모집글 삭제 시 연관 데이터
- `deleteRecruitPost`가 모집글만 삭제해 신청 문서·알림이 남음 → 신청 내역에 없는 글이 남고, 알림 클릭 시 404
- 해결: 연관 문서를 함께 삭제하거나 신청을 "삭제된 모집" 상태로 전환
- 처리: 모집글 삭제와 같은 배치에서 신청 문서 삭제, 대기·수락 신청자에게 `recruit_deleted` 알림 전송
- 규칙: 모집글이 없는(같은 배치에서 삭제되는) 경우에만 작성자의 신청 문서 삭제 허용
- 남은 점: 이 변경 이전에 삭제된 글의 신청 문서(고아 데이터)는 그대로 남아 있음. 기존 알림의 링크는 상세 페이지의 "게시글을 찾을 수 없어요" 화면으로 연결됨

### 4. 만료 글 자동 마감
- `docs/features/모집자동마감.md`는 목록에서 만료 글 발견 시 `closed`로 저장한다고 하지만, `useRecruitPosts`는 화면에서 숨기기만 함 (상세 페이지 진입 시에만 저장)
- 해결: 목록에서도 Firestore에 마감을 저장하도록 구현. 마감 대상 선별은 `selectPostsToClose`(`src/lib/utils/recruitExpiry.ts`) 순수 함수로 분리하고 단위 테스트 추가
- 중복 쓰기는 `useRef`에 시도한 postId를 기록해 세션당 글마다 1회로 제한. 보안 규칙(`firestore.rules` 66-71행)이 경기 시간이 지난 글의 `status`/`updatedAt` 변경만 허용
- 서버 보정(#59): Vercel Cron이 하루 한 번 최근 3일 경기 중 지난 글을 마감하고 대기 신청을 정리한다 (`docs/features/모집자동마감.md` 8장). 배포 환경 변수 `CRON_SECRET` 필요
- 남은 점: 서버 보정은 하루 1회(Hobby 플랜 제한)라 그 사이에는 클라이언트 경로에 의존한다

### 5. 마감·재오픈 후속 처리
- 마감 시 대기 중인 신청이 그대로 남고 신청자에게 알림이 없음
- 정원이 찬 상태에서도 재오픈 가능
- 처리: 작성자 마감·정원 충족 자동 마감 시 대기 신청을 `closed`(모집 마감)로 바꾸고 `recruit_closed` 알림 전송, `applicantIds`에서 제외해 재오픈 시 재신청 가능
- 재오픈은 트랜잭션에서 정원·경기 시간 검증 (`assertCanReopen`)
- 규칙: 작성자가 대기 신청을 `closed`로 바꾸는 것 허용
- 경기 시간 경과 자동 마감의 대기 신청 처리: 자동 마감은 아무 로그인 사용자가 수행하고 그 사용자는 남의 신청 문서를 바꿀 권한이 없으므로, 권한이 있는 **작성자가 자기 글을 열 때 뒤늦게 정리**한다 (규칙 변경 없이 해결)
  - 판정은 `hasUnclearedPendingApplications` / `selectPostsToCleanup` 순수 함수 (`applicationRules.ts`). `applicantIds`(대기 + 수락)와 `acceptedCount`(수락)의 차이로 대기 신청 잔여를 판단하므로 추가 읽기가 필요 없다
  - 트리거: 내 모집글 목록(`useMyRecruitPosts`), 모집글 상세(작성자 본인). 세션당 글마다 1회만 시도(`useRef`)
  - 정리 전이라도 신청 목록에서는 `displayApplicationStatus`로 "마감"으로 표시하고 수락·거절 버튼을 숨긴다 (마감된 글은 수락이 거부되므로)
- 작성자가 접속하지 않는 경우는 서버 보정(#59)이 하루 한 번 정리하고 알림을 보낸다
- 남은 점: 신청자 화면의 `대기중` 표시는 최대 하루 늦게 바뀔 수 있다. 수정 페이지에서 모집 인원을 수락 인원보다 적게 줄이는 것도 막지 않음

### 6. 페이지네이션
- 모집글·채팅 메시지·알림 쿼리에 `limit`이 없어 전체를 실시간 구독
- 해결: 커서 기반 페이지네이션 또는 무한 스크롤
- 처리: 실시간 구독을 유지하면서 limit을 "더 보기"로 늘리는 방식 (`usePageLimit`)
  - 모집글 20개, 알림 20개, 채팅 메시지 최근 50개(`limitToLast`)부터 표시
  - 안 읽은 알림 수는 별도 쿼리(recipientId·isRead 등호 조건, 최대 100개)로 분리해 헤더 배지가 목록 범위와 무관하게 동작
  - 채팅방별 안 읽은 메시지 수와 읽음 처리는 최근 100개 메시지만 확인
- 채팅방·알림 구독 중복 제거: Header·BottomNav·채팅 목록·알림 페이지가 각각 같은 구독을 열던 것을 `AppDataProvider`(`src/contexts/AppDataContext.tsx`)에서 한 번만 구독해 공유하도록 바꿨다. 알림 목록은 페이지네이션이 필요해 페이지 훅을 유지한다
- 커서 페이지네이션(#60): `usePageLimit`(limit을 늘려 재구독)을 `useLivePagedQuery`로 교체
  - 첫 페이지만 실시간 구독하고 이전 페이지는 `startAfter` 커서로 한 번씩만 읽는다. N페이지까지 볼 때 읽기가 20+40+…+20N에서 약 20(N+1)로 줄어든다
  - 더 보기를 처음 누를 때 실시간 구간 끝을 `endAt`으로 고정해, 새 문서가 들어와도 경계 문서가 빠지지 않게 한다
  - 채팅 메시지는 최신순으로 받아 화면에서 뒤집는다
- 모집글 필터(#60): 날짜·지역·실력·검색어는 부분 일치 등 쿼리로 표현할 수 없어 받아온 글에 적용하되, 조건에 맞는 글이 한 페이지 분량 모일 때까지 다음 페이지를 자동으로 이어 받는다(한 번에 최대 5페이지, 이후 "조건에 맞는 글 더 찾기")
- 남은 점: 이어 받은 이전 페이지는 한 번 읽은 값이라 이후 변경(마감·삭제·읽음)은 새로고침 전까지 반영되지 않는다
