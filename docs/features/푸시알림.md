# 푸시 알림(FCM) 기능명세서

> 관련: #16 (인앱 알림) — 이번 작업은 그 위에 웹 푸시를 더한다

## 1. 개요

인앱 알림(`notifications` 컬렉션)이 생길 때 받는 사람의 브라우저로 **웹 푸시**를 보낸다.
앱을 닫아 두었거나 다른 탭을 보고 있어도 새 메시지·신청 결과를 알 수 있게 한다.

### 범위

| 항목 | 상태 |
|---|---|
| 웹 푸시 (Chrome·Edge·Firefox·macOS Safari) | **이번 작업** |
| 마이페이지에서 푸시 켜기 | **이번 작업** |
| 알림 종류별 수신 설정 | 제외 — 전부 받거나 전부 끄기 |
| iOS Safari | 제외 — 홈 화면에 추가한 PWA에서만 웹 푸시가 되므로 매니페스트 작업이 먼저 필요 |
| 네이티브 앱 푸시 | 제외 |

## 2. 전체 흐름

```
[받는 사람 브라우저]                         [서버 /api/push]                     [FCM]
마이페이지 "푸시 알림" 켜기
 → 알림 권한 요청
 → 서비스 워커 등록 (/firebase-messaging-sw.js)
 → getToken(VAPID 키) → 토큰
 → fcmTokens/{토큰} 저장 ({ uid })

[보내는 사람 브라우저]
알림 문서 생성(기존 코드) 커밋 성공
 → requestPush([알림 ID…])  ─────────▶  ID 토큰 검증
   (응답을 기다리지 않음)                   알림 문서 읽기 → 보낼 대상인지 판정
                                            pushedAt 기록 (중복 발송 방지)
                                            fcmTokens에서 uid == 받는 사람 조회
                                            messages:send  ────────────────▶  브라우저로 전달
                                            만료 토큰 삭제

[받는 사람 서비스 워커]
push 이벤트 → 시스템 알림 표시 (앱을 보고 있으면 소리 없이)
알림 클릭 → link 열기 (이미 열린 탭이 있으면 그 탭으로 이동)
```

발송 방식은 **Next API 라우트(a안)**. Cloud Functions(b안)는 Blaze 요금제와 별도 배포가 필요해 택하지 않았다.
서버 크론(`/api/cron/close-expired-posts`)이 만드는 알림은 크론 안에서 같은 발송 함수를 바로 호출한다.

## 3. 토큰 저장

### 3-1. 위치

`fcmTokens/{token}` — 최상위 컬렉션, 문서 ID가 토큰이다. **기기(토큰)당 문서가 하나**다.

```ts
{ uid: string, updatedAt: Timestamp }
```

- 같은 브라우저에서 다른 계정으로 로그인하면 새 계정이 같은 문서를 덮어써 소유자(`uid`)가 바뀐다. 로그아웃 처리가 빠지거나 실패해도 한 기기가 두 계정의 푸시를 함께 받지 않는다
- 처음에는 `users/{uid}/fcmTokens/{token}` 하위 컬렉션이었으나, 이 구조에서는 이전 계정의 토큰 문서를 새 계정이 지울 수 없어 위 문제가 생겨 바꿨다 (PR #71 리뷰)
- `users` 문서 필드에 두지 않는 이유: `users` 문서는 로그인 사용자 전체가 읽을 수 있다. 토큰은 소유자만 읽는다

### 3-2. 등록 시점

- **마이페이지 → 계정 → 푸시 알림** 행을 눌러 켠다. 페이지 진입만으로 권한을 묻지 않는다 (브라우저가 거절 이력을 남기면 다시 물을 수 없음)
- 이미 권한이 허용된 사용자는 로그인할 때마다 `getToken`으로 토큰을 새로 받아 저장한다 (FCM 토큰은 바뀔 수 있음)
- 권한 상태별 표시

| `Notification.permission` | 표시 | 동작 |
|---|---|---|
| `default` | "꺼짐" | 누르면 권한 요청 → 허용 시 토큰 저장 |
| `granted` + 토큰 저장됨 | "켜짐" | — |
| `denied` | "차단됨 — 브라우저 설정에서 허용" | 누를 수 없음 |
| 미지원 브라우저 | "이 브라우저는 지원하지 않아요" | 누를 수 없음 |

### 3-3. 삭제 시점

- 로그아웃: 이 기기 토큰 문서를 지우고 `deleteToken`으로 토큰을 폐기한 뒤 로그아웃한다 (공용 기기에서 다른 사람 알림이 오지 않게)
  - `deleteToken`은 그 전에 `getToken`으로 서비스 워커를 지정하지 않으면 기본 서비스 워커를 따로 등록하므로, 우리 서비스 워커로 `getToken`을 먼저 부른다
- 발송 시 FCM이 `UNREGISTERED`/`INVALID_ARGUMENT`(토큰 형식)로 응답한 토큰: 서버가 지운다

## 4. 발송 API — `POST /api/push`

### 4-1. 요청

```
Authorization: Bearer <Firebase ID 토큰>
{ "notificationIds": ["…", "…"] }   // 최대 50개
```

클라이언트는 `src/lib/services/pushService.ts`의 `requestPush(ids)`로 호출한다. 실패해도 무시한다 (인앱 알림은 이미 저장됐다).

### 4-2. 판정 (`src/lib/server/pushRules.ts`, 순수 함수)

알림 문서마다 아래를 모두 만족해야 보낸다.

| 조건 | 이유 |
|---|---|
| 문서가 존재 | — |
| `pushedAt` 없음 | 같은 알림을 두 번 보내지 않음 |
| `createdAt`이 2분 이내 | 오래된 알림을 다시 울리는 악용 방지 |
| `recipientId` ≠ 호출자 | 자기 자신에게는 보내지 않음 (알림 생성 규칙과 같음) |
| `senderId` = 호출자 | 호출자가 만든 알림만 보냄 (크론은 해당 없음) |

`pushedAt`은 `updateTime` 사전 조건을 걸어 기록한다. 동시에 두 요청이 와도 하나만 성공해 한 번만 발송된다.
사전 조건 실패는 "다른 요청이 이미 보냄"으로 보고 건너뛰고, 그 밖의 오류(네트워크, 5xx)는 로그를 남기고 `errors`로 센 뒤 다음 알림을 계속 처리한다.
`pushedAt`을 발송 전에 기록하므로 FCM 발송이 실패한 알림은 다시 보내지 않는다 (중복 발송보다 누락을 택함).

**제목은 서버가 만든다.** 알림 문서의 `title`·`body`는 작성자가 마음대로 쓸 수 있어, 그대로 OS 알림에 띄우면
"[관리자] 계정 확인 필요" 같은 피싱 문구를 다른 사용자에게 보낼 수 있다 (PR #71 리뷰). 그래서 클라이언트가 만든 알림은

- 제목: 알림 종류(`type`)와 보낸 사람의 **현재 닉네임**(`users/{senderId}`)으로 서버가 만든다 — 예: `Alice님의 새 메시지`, `Alice님이 참가 신청을 수락했어요` (`clientPushTitle(type, senderName)`)
  - 모르는 종류는 보내지 않는다. 종류는 템플릿 표의 **자기 속성**(`Object.hasOwn`)으로만 찾는다. `type: "constructor"`·`"__proto__"` 같은 프로토타입 키로 템플릿이 아닌 함수가 잡히지 않게 한다
  - 닉네임이 없거나 현재 규칙(`isValidDisplayName`: 앞뒤 공백 없음, 2~12자, 금지 문자 없음, `프로필수정.md` 3장)에 맞지 않으면 이름 없이 종류별 기본 제목을 쓴다. 규칙이 생기기 전에 저장된 긴 이름("[관리자] 계정 확인 필요 …")이나 방향 제어 문자가 든 이름이 제목에 실리지 않게 한다

| 종류 | 이름이 있을 때 | 이름이 없거나 규칙에 맞지 않을 때 |
|---|---|---|
| `new_message` | `{이름}님의 새 메시지` | 새 메시지가 도착했어요 |
| `application_received` | `{이름}님이 참가 신청했어요` | 새 참가 신청이 도착했어요 |
| `application_accepted` | `{이름}님이 참가 신청을 수락했어요` | 참가 신청이 수락되었어요 |
| `application_rejected` | `{이름}님이 참가 신청을 거절했어요` | 참가 신청이 거절되었어요 |
| `recruit_deleted` | `{이름}님이 모집을 취소했어요` | 모집이 취소되었어요 |
| `recruit_closed` | `{이름}님의 모집이 마감되었어요` | 모집이 마감되었어요 |

- 본문: `body`를 100자로 잘라 쓴다

이름이 규칙에 맞으면 누가 보냈는지가 제목에 드러난다. 보낸 사람의 `users` 문서가 없어도 기본 제목으로 보낸다. 크론이 만든 알림(서버 작성)은 문서의 `title`을 그대로 쓴다.

**남은 한계:** 보낸 사람과 받는 사람의 관계(같은 채팅방인지, 내 모집글 신청자인지)는 확인하지 않는다. 로그인한 사용자는 자기 닉네임이 드러나는 푸시를 임의의 사용자에게 보낼 수 있다 (스팸). 필요해지면 종류별로 관계 확인을 추가한다.

### 4-3. 메시지

데이터 메시지로 보내고 표시는 서비스 워커가 한다 (`notification` 페이로드를 쓰지 않음).

```json
{
  "message": {
    "token": "…",
    "data": { "title": "(서버가 만든 제목)", "body": "(100자 이하)", "link": "/chat/abc", "notificationId": "…" },
    "webpush": { "headers": { "Urgency": "high", "TTL": "86400" } }
  }
}
```

`link`는 클라이언트가 쓰는 값이라 `src/lib/utils/internalLink.ts`의 `isInternalPath`를 통과한 앱 내부 경로만 싣고, 아니면 `/notifications`로 바꾼다. `/`로 시작하되 `//`·역슬래시·제어 문자(탭·줄바꿈 등 URL 파서가 지우는 문자)·공백을 거부하고, 실제로 URL로 해석해 출처가 바뀌지 않고 경로가 `//`로 시작하지 않는지 확인한다 (`"/\t/evil.com"`은 탭이 지워져 `//evil.com`이 되고, `"/.//evil.com"`은 경로가 `//evil.com`으로 정규화된다).

### 4-4. 인증

`firebase-admin`은 쓰지 않는다 (기존 `firestoreRest.ts`와 같은 이유 — 서버리스 ESM 문제).

| 할 일 | 방식 |
|---|---|
| ID 토큰 검증 | Google `securetoken` 공개 인증서로 `jsonwebtoken.verify` (RS256, `aud`=프로젝트 ID, `iss`=`https://securetoken.google.com/<프로젝트 ID>`) |
| Firestore 읽기·쓰기 | 기존 `firestoreRest.ts` |
| FCM 발송 | 서비스 계정 OAuth 토큰(`firebase.messaging` 범위)으로 HTTP v1 `messages:send` |

OAuth 토큰 발급은 `src/lib/server/googleAuth.ts`로 분리해 Firestore·FCM이 범위별로 캐시해 함께 쓴다.

## 5. 서비스 워커 — `public/firebase-messaging-sw.js`

Firebase SDK를 불러오지 않는 순수 서비스 워커다 (설정값을 주입할 필요 없음).

- `push`: 페이로드의 `data`를 꺼내 **항상** `showNotification`. 보이는(visible) 앱 탭이 있으면 `silent: true`로 소리·진동 없이 띄운다
  - 앱을 보고 있을 때 알림을 생략하면 안 된다. Safari·iOS는 알림 없이 끝난 푸시가 반복되면 구독을 취소한다 (PR #71 리뷰)
- `notificationclick`: 알림을 닫고 같은 출처의 열린 탭이 있으면 포커스 후 `link`로 이동, 없으면 새 창
  - 서비스 워커는 TS를 불러올 수 없어 `safeLink`에 `isInternalPath`와 같은 검사를 옮겨 두고, 연 URL의 출처가 `self.location.origin`과 다르면 `/notifications`를 연다
- 같은 `notificationId`는 `tag`로 묶어 중복 표시를 막는다

## 6. 알림 생성 위치별 발송

| 알림 종류 | 생성 위치 | 발송 |
|---|---|---|
| `new_message` | `useMessage.sendMessage` | `requestPush([id])` |
| `application_received` | `applicationService.applyToPost` | `requestPush([notiRef.id])` |
| `application_accepted` | `applicationService.acceptApplication` | 〃 |
| `application_rejected` | `applicationService.rejectApplication` | 〃 |
| `recruit_closed` (작성자) | `applicationService.closePendingApplications` | 커밋 후 생성한 ID 전부 |
| `recruit_deleted` | `recruitService.deleteRecruitPost` | 〃 |
| `recruit_closed` (크론) | `expiredPostsJob.closeExpiredPosts` | 서버에서 `sendPushForNotifications` 직접 호출 |

## 7. 보안 규칙

```
match /fcmTokens/{token} {
  allow read, delete: if signedIn() && resource.data.uid == request.auth.uid;
  allow create, update: if signedIn()
    && request.resource.data.uid == request.auth.uid
    && request.resource.data.keys().hasOnly(['uid', 'updatedAt']);
}
```

`update`가 다른 사람 소유 문서도 허용하는 것은 의도다 (3-1: 같은 기기에서 계정이 바뀌면 소유자를 바꾼다). 토큰 값을 아는 기기만 그 문서 경로를 알 수 있다.

`notifications` 생성 규칙에 추가한 조건:

- `senderId`는 있으면 작성자 uid와 같아야 한다 (`buildNotification`이 `auth.currentUser.uid`를 넣는다). 이전 버전 클라이언트가 열어 둔 탭은 `senderId` 없이 만들므로 필수로 하지 않았다 — 그런 알림은 인앱에만 보이고 푸시는 가지 않는다
- `createdAt == request.time` — 2분 이내 판정이 클라이언트 시각에 속지 않게 한다

`notifications`의 `pushedAt`은 서버(서비스 계정)만 쓴다. 클라이언트 생성 규칙의 `hasOnly` 목록에 없으므로 클라이언트가 미리 넣을 수 없다.

## 8. 환경 변수

| 이름 | 용도 |
|---|---|
| `NEXT_PUBLIC_FIREBASE_VAPID_KEY` | `getToken`의 웹 푸시 인증서 공개 키 (콘솔 → 프로젝트 설정 → 클라우드 메시징) |
| `FIREBASE_ADMIN_CLIENT_EMAIL`, `FIREBASE_ADMIN_PRIVATE_KEY` | 기존 값 재사용 (FCM 발송) |

Vercel에도 `NEXT_PUBLIC_FIREBASE_VAPID_KEY`를 추가해야 배포 환경에서 동작한다.
서비스 계정에 FCM 발송 권한(`cloudmessaging.messages.create`)이 필요하다. Firebase가 만든 `firebase-adminsdk` 계정에는 기본으로 있다.
